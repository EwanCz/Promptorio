# Promptorio — Implementation Reference

Historical snapshot of implemented features and integration notes, extracted from the original plan. It may contain outdated API details; the code, `docs/CONTEXT.md`, and `docs/UI.md` are authoritative. Update or replace relevant reference material when behavior changes. Open work is tracked in issues, not here.

## Decisions
- **LLM:** provider-agnostic adapter (`LLMProvider`). `AnthropicProvider` and `OpenAIProvider` (both with an optional relay base URL), plus a deterministic `MockProvider`. Neither real provider has been run against its live API: tests use scripted responses.
- **API key:** player-entered in a settings UI, stored in `user://settings.cfg`. A dev can also put it in a git-ignored `.env` at the project root (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, see `.env.example`). The key saved from the dialog wins, `.env` is the fallback. `.env` is only read by the editor build (`OS.has_feature("editor")`), never saved to `settings.cfg`, never shown in the dialog, never exported or committed.
- **Chip triggers:** only the fixed timer and a manual "Ask now" button. No state or event ever wakes a chip: not OVERHEATING or any temperature, not error / output full / input empty. The machine state (temperature, status, enabled, cooling, emergency_stop) is sent whenever a chip is asked, so a chip can act on it then. `ChipComponent` has no threshold API and machines have no `get_events()`.
- **Chips and prompts:** a machine can have several chips. Each chip has exactly one prompt and its own timeout, cooldown and in-flight slot, so chips never compete with each other.
- **Simulation clock:** physics-driven, with elapsed-time catch-up at 10 Hz; paused time is excluded.
- **Prototype build economy:** start with 100 money. Build costs: Miner 20, Smelter 30, Assembler 40, Conveyor 2, Orchestrator 150 (expensive on purpose; needs playtesting). The map-center Collector is free and fixed. Charge only after a valid placement; destroying a machine from the tooltip refunds half its price (rounded down); an exploded Smelter refunds nothing.
- **Team and scope:** 2-3 devs, one tight loop (Miner -> Smelter -> Assembler) with a visible win/fail state. Conveyors are plain logic. AI on conveyors and logistics nodes is post-MVP.

Architecture and async HTTP rules live in `CLAUDE.md`.

### Autoload API (for Machine / ChipComponent / UI work)
- `LLMManager.request_decision(requester_id: int, system_prompt: String, state: Dictionary, tools: Array)`. `requester_id` is `get_instance_id()`. Results come back as `decision_received(requester_id, tool_calls: Array[Dictionary])` (each `{name, args}`) or `decision_failed(requester_id, reason)`. A queued request replaced by a newer one from the same requester fails with `"superseded"`. Re-validate with `is_instance_valid(instance_from_id(id))` on receipt.
- Tool schema format (what `get_tool_schemas()` returns): `{name, description, input_schema: {type: "object", properties: {key: {type: "number"|"integer"|"boolean", minimum, maximum}}}}`.
- `GameState`: `TICK_RATE`, `GRID_SIZE`, `CELL_SIZE`, `tick_count`, `money`, `can_place(cell)`, `register_machine(machine, cell) -> bool`, `unregister_machine(cell)`, `get_machine_at(cell)`, `get_machines()`, `cell_to_world(cell)`, `world_to_cell(pos)`, `add_money(amount)`.
- `EventBus` signals: `tick_fired(tick)`, `machine_exploded(machine)`, `machine_registered/unregistered(machine, cell)`, `machine_selected(machine)`, `money_changed(amount)`, `chip_log_added(machine, message)`, `settings_changed`, `chip_registered/chip_removed(chip)` (emitted by `ChipRegistry`), `llm_request_started(requester_id)`, `llm_request_finished(requester_id, success)` (emitted by `LLMManager`). `Settings.provider` accepts `"mock"` or `"anthropic"`.
- `Settings`: `api_key`, `provider` (`"mock"` for now), `model`, `max_concurrency`, `request_timeout`, `chip_cooldown`, `max_tokens`, `save_settings()`. Keys: `get_api_key(provider)` is the key the game sends (saved key, else `.env`), `get_saved_api_key(provider)` only the dialog one, `get_key_source(provider)` is `"settings"`, `".env"` or `""`. `load_env()` reads `env_path` (default `res://.env`) at startup in the editor.
- Tests: `tests/run.sh [filter]` runs every `tests/test_*.gd` headless (~15 s, exit 1 on failure). How to write tests: see "Testing" in `CLAUDE.md`.
- Headless gotcha: after adding a new `class_name` script, run `godot --headless --import` once to refresh the class cache, otherwise it fails to parse. `godot --headless --quit` still errors until a main scene exists.

### Machine / chip API
- `Machine` (`scripts/machines/machine.gd`): `get_tool_schemas()` (the shared tools, then the type's own `_own_tool_schemas()`), `get_state() -> Dictionary` (compact: `type`, `enabled`, `status`, plus subclass fields), `apply_tool_call(name, args) -> bool` (whitelists the name, requires every schema arg, type-checks and clamps, then calls the `_apply()` override), `log_chip(message)` (emits `chip_log_added`). Shared tool: `set_enabled(on: bool)`. Miner exposes `set_mine_ticks` (current resource's minimum..100) and `set_mined_item`; Smelter exposes `set_cooling`, `set_emergency_stop`, `set_product` and `discard_stock`; Assembler exposes `set_stock_limit`, `set_product` and `discard_stock`; Conveyor exposes `set_direction` (0..3: right, down, left, up); Collector exposes `set_accepting`. See the AI tool inventory for arguments and behavior. `status` is `Machine.Status` (`NORMAL`, `DOWN`, `OVERHEATING`).
- `ChipRessource` (`scripts/chip/chip_ressource.gd`, a `Resource`, pure data): `id`, `name`, `description`, `prompt`.
- `ChipRegistry` (autoload, `scripts/chip/chip_registry.gd`): `add(name, prompt, desc = "") -> ChipRessource` (null if the name is empty or taken), `remove(id) -> bool`, `get_from_id(id)`, `get_all()`. Emits `EventBus.chip_registered/chip_removed`.
- `ChipComponent` (`scripts/chip/chip_component.gd`, a `Node`, child of the `Machine`): holds a `ChipRessource` (`chip`), `timeout` (ticks between timer calls, `set_timeout()`), `pending`. `call_llm(reason) -> bool` asks the LLM; cooldown (`Settings.chip_cooldown`) and one request in flight apply per chip. The answer goes through `Machine.apply_tool_call`; signal `decision_applied(reason, applied)`. Only the timer and manual "Ask now" trigger a request. A trigger dropped by the cooldown or an in-flight request is not queued; the timer is the fallback. The reason (`timer` or `manual`) is passed to `decision_applied` and logged.
- `Machine`: `chips: Array[ChipComponent]`, `attach_chip(chip_id, timeout_ticks) -> ChipComponent` (null if unknown or already attached), `detach_chip(id)`, `get_chip(id)`, signal `chip_decision_applied(chip_id, reason, applied)`.
- Scenes: `scenes/menu/main_menu.tscn` is the project main scene, `scenes/main.tscn` is the factory, and `scenes/machines/machine.tscn` is the base machine.

### Simulation (track B, done)
- [x] Chain Miner -> Smelter -> Assembler -> Collector over plain `Conveyor`s, driven by `EventBus.tick_fired`. `Machine` gained `facing`, `receive(item) -> bool` (default refuses), `_tick()` (override per type, skipped while `DOWN`) and `_push(item)` (hands an item to the machine in front). Items are strings, the ids of the resource catalog (`ore` -> `ingot` -> `part` is the default chain).
- [x] `Miner`: 1 unit of its resource per `mine_ticks` (the resource's own mining time, 20 for ore), stalls while its output is blocked. `CraftMachine` (base of `Smelter` and `Assembler`): stock of any resource capped per item at 10, builds its `product_id` from the stock (inputs and ticks come from the catalog, see "Resources"), blocked output stalls it. `Collector` buys every catalog resource at its catalog price and refuses anything else. `Conveyor` holds one item and moves it on after 5 ticks.
- [x] Resources (`ItemData`, `ItemCatalog`, `data/items.tres`): a resource has an `id`, a `display_name`, a `price`, the only `machine` type that builds it, its `inputs` (id -> count, empty when mined) and `ticks` (craft time in a smelter or assembler; mining time for a mined resource, which is also the fastest a miner can go on it). `ItemCatalog.shared()` loads the file once; `get_item`, `has_item`, `price_of`, `get_built_by(machine_type)` (file order, the first is the machine's default), `get_ids`. Shipped catalog: Each resource has a 32x32 pixel `icon` (`assets/items/<id>.png`, CC0, sources in `assets/items/CREDITS.md`; power and circuit are drawn in-house); a Conveyor draws the icon of the item it holds (`ItemIcon` sprite in `conveyor.tscn`) instead of the old dot. The icon slides in from the sender's cell over `MOVE_TICKS` (`Machine.note_sender()`, `Conveyor.get_slide_progress()`). A conveyor takes exactly `MOVE_TICKS` ticks whichever machine plays first in a tick (`note_sender(cell, tick)` tells it whether its own turn in the sender's tick is still to come), and `GameState.tick_fraction()` adds the time since the last physics step, so the glide is even on every frame.

  A crafted resource always sells for more than its inputs (checked in `tests/test_items.gd`). Wood and the spear were removed.

  Rules: a resource is only built by its own machine type: the check is `ItemData.is_built_by(machine_type)` inside `set_product` / `set_mined_item`, which return false and change nothing otherwise (`_apply` returns that to `apply_tool_call`, which logs `ignored ...: the machine refused it` and does not emit `tool_applied`); the tool description lists the resources the machine may build, but only the function decides; a machine with no known type builds nothing; any catalog resource can be stored in a smelter or assembler (up to `stock_limit` each), needed or not, and only `discard_stock` removes it; a craft needs every input in its full count; changing the product lets the running craft finish as the old product (its inputs are already spent). Mined resources take time too: more valuable ones are slower (ore 20, coal 25, silver 35, redstone 40, diamond 80 ticks). Defaults: Miner ore, Smelter ingot (`product_id` in `smelter.tscn`), Assembler part (`assembler.tscn`). Adding a resource is a new entry in `data/items.tres` and nothing else; `tests/test_items.gd` checks the catalog is consistent (unique ids, known inputs, no cycles, positive prices and times). `Recipe` and `data/recipes/` are gone. Not done: there is no way for the player to pick the product without a chip (tool calls only).
- [x] Conveyor behavior: a conveyor is an ordinary placed machine with a facing direction. On each 10 Hz simulation tick it advances its held item; after 5 ticks it tries to deliver that item to the machine in the adjacent cell it faces. If the cell is empty or the machine refuses the item, it keeps the item and retries on later ticks. A conveyor accepts only one item at a time. Machines can also pass items directly to an adjacent machine, so conveyors are optional links rather than automatic belts between every machine.
- [x] Smelter temperature: working +0.6/tick, idle -0.3/tick, floor 20. `set_cooling(on)` is a production trade-off. Cooling off runs flat out: crafts take half the recipe time (`UNCOOLED_SPEEDUP = 2`, so 10 ticks for the 20-tick smelt recipe). While cooling is on, crafts take twice the recipe time (`COOLED_CRAFT_FACTOR`, 40 ticks), so cooling off makes 4x the ingots (measured over 150 ticks with ore always available: 12 vs 3). Both factors apply when a craft starts. Other numbers unchanged: heat while working +0.6/tick, idle -0.3/tick. An unattended fast smelter still overheats and explodes, measured at 287 ticks (about 29 s; it idles one tick in eleven between crafts, so it is a little slower to blow than before, ~22 s). The art reddens from 60° (white) to fully red at 150° (`Smelter._update_heat_tint`) and trembles from 100° (the overheating line, `SHAKE_FROM`) up to 150°: `Smelter.shake_amplitude(heat)` is exactly 0 up to 100° and grows cubically, so it is almost invisible until about 120° (0.03 px at 110°, 0.26 px at 120°, 1.4 px at 135°, 4 px at 150° = `SHAKE_MAX_PIXELS`), at 25 Hz. Only the sprite moves: `Machine` keeps `_sprite_home` (set by `_update_sprite` for the facing) and `_sprite_offset`, and always places the sprite at home + offset, so nothing accumulates, a rotation mid-shake re-centres it, the offset is reset to zero the moment it explodes (the flash plays on the resting art), and it falls back to zero as it cools. The machine node, its cell, facing and the simulation are untouched. Tested in `tests/test_simulation.gd`. With cooling on it stays stable, at a quarter of the cooling-off throughput. The stop stays local to the one smelter (no factory-wide stop). `set_emergency_stop(on)` is the Cooler's emergency tool: `true` disables the smelter and sets `emergency_stop` (in the state); `false` resumes it only if `emergency_stop` is still set, so a pause from another chip is never undone. Any `set_enabled` call clears the marker. Starter `Smelter Cooler`: cooling on at 100° and off at 70° as normal management, `set_emergency_stop(true)` at 130° (after `OVERHEATING` begins at 100°, before explosion at 150°), `set_emergency_stop(false)` at 80° or below while `emergency_stop` is true. If disabled without `emergency_stop`, it stays disabled because the state does not reveal why it was disabled. The Smelter exposes the shared `set_enabled` and its own `set_cooling` and `set_emergency_stop` tools. A `user://chip_registry.tres` saved with an earlier, unedited starter prompt is upgraded on load (`ChipRegistry.OUTDATED_STARTER_PROMPTS`, matched by md5, same id and name); edited or custom prompts are never touched.
- [x] Assembler production modes (`scripts/machines/assembler.gd`): `normal` (default) is the recipe unchanged; `fast` needs `FAST_INPUT_MULTIPLIER` (2) times each input of the product and finishes in the recipe time divided by `FAST_TIME_DIVISOR` (2, rounded down, floored at 1 tick). `CraftMachine` grew an overridable `_scale_inputs(product)` (default: the recipe as-is) behind a public `get_effective_inputs()`, read everywhere the base class reads the recipe: `get_state()`'s `needs`, `_can_start()` and the stock consumed when a craft starts. So a craft in fast mode that lacks the extra inputs simply never starts (`_can_start` checks the scaled recipe) — it is never silently built at the normal cost. Both the cost and the duration are fixed the moment a craft starts (same mechanism as the Smelter's `cooling`: changing `mode` mid-craft only affects the next one). `set_mode(mode: "normal"|"fast")` is the tool; `mode` is in `get_state()` and persisted (`_save_data()`/`_load_data()`); an unrecognized saved value falls back to `normal`. In-world feedback: the sprite is tinted a light warm color in fast mode (`Assembler.FAST_TINT`, reset to white in normal mode); the tooltip's recipe row leads with a mode icon (`Icons` `mode_fast` / `mode_normal`) and its quantities are `get_effective_inputs()`, so they already reflect the active mode (`MachineTooltip._refresh_operation`). Tests: `tests/test_assembler_modes.gd`.
- [x] Placement (`Placement`, `scripts/world/placement.gd`, node in `World`): Input Map actions (physical-key defaults, layout independent) `select_miner` / `select_smelter` / `select_assembler` / `select_conveyor` (`1`, `2`, `3`, `5`), `rotate_placement` (`R`, facing right, down, left, up) and `cancel_placement` (`Esc`) drive it; `Main` forwards them to `Placement.handle_input()`; left click on a grid cell places. Refuses out-of-grid, occupied cells, and miners off a minesite. The Collector is placed at the map center on start and is not selectable: no action, no Build page entry, and `select` / `try_place` refuse it. Machines unregister themselves from `GameState` when freed. `Placement.select(type)` is what both the shortcuts and the Build page call; `place(type, cell)` applies the rules without cost and `try_place(type, cell)` adds the `COSTS` charge (once, only on success; emits `placement_rejected(reason)` otherwise).
- Head-on rule: two machines facing each other (`target.facing == -facing`) pass nothing to one another, in either direction (`Machine._push`), e.g. a smelter facing a conveyor that points back at it: both stay blocked until one is turned. The Collector has no facing and never counts. Test: `tests/test_simulation.gd`.
- Prototype conveyor controls: trigger `select_conveyor` (`5`) to select a conveyor, `rotate_placement` (`R`) to rotate its output direction clockwise, then left-click a free grid cell to place it. The direction is shown by the belt art and the tooltip (no arrow label over the machine); the status label is only a dot while it holds an item. No machine shows its name over it any more: the label is empty except the smelter temperature / BOOM and the conveyor dot. The Build page selects the same types through `Placement.select`.
- Paid placement, machine removal/rotation, the Build page and the tooltip actions are track C and are done (see "Bar and popups" below). The hover highlight follows the selected machine's rule (see "Grid and camera").

### AI tool inventory (as implemented)
What `get_tool_schemas()` returns per machine: the shared tool first, then the tools unique to the type (`_own_tool_schemas()`). Every argument is required; a missing or wrongly typed value rejects the whole call (`discard_stock`'s `item` must also be a catalog id) (logged to the ChipLog, machine unchanged), and integers are clamped to their range. A chip can be attached to any machine, including the Collector and conveyors, so all five types are listed. Checked in `tests/test_machine_tools.gd` and `tests/test_chip_integration.gd`.

| Tool | Args | Offered by | Effect |
|------|------|------------|--------|
| `set_enabled` | `on: boolean` | every machine (inherited from `Machine`) | Sets `enabled`; see the per-machine effect below. |
| `set_mine_ticks` | `ticks: integer`, (the resource's mining time)..100 | Miner | Ticks per unit; lower is faster, but never below the mining time of the current resource (`Miner.get_min_mine_ticks()`: ore 20, diamond 80). A chip can only slow a miner down. `set_mined_item` resets it to the new resource's time. |
| `set_mined_item` | `item: string` | Miner | Calls `Miner.set_mined_item(item) -> bool`: fails (nothing changes; the ChipLog line says why, e.g. `'ingot' cannot be made by this miner: it is built by smelters`) unless the catalog says a `miner` builds it; else sets the resource mined from now on (default `ore`). A unit already held is pushed on as it was. Also refused (and nothing changes) outside `MINING` mode, so the resource stays the same through a prospect/boost cycle. |
| `start_prospecting` | none | Miner | Calls `Miner.start_prospecting() -> bool`: fails while already prospecting or boosted (a cycle cannot restart mid-way); else pauses mining for `PROSPECT_TICKS` (80, 8s at 10Hz), then mines at `BOOST_RATE` (2x) the current `mine_ticks` for `BOOST_TICKS` (200, 20s) before returning to `MINING` on its own. See "Miner prospecting" below. |
| `set_product` | `item: string` | Smelter, Assembler | Calls `CraftMachine.set_product(item) -> bool`: fails (nothing changes; the ChipLog line says why, e.g. `'circuit' cannot be made by this smelter: it is built by assemblers`) unless the catalog says this machine's type builds it; else sets the resource built from now on. The running craft finishes first. |
| `discard_stock` | `item: string` (any resource), `count: integer`, 1..10 | Smelter, Assembler | Throws away up to `count` units of a stored resource. The only way to empty a stock. |
| `set_cooling` | `on: boolean` | Smelter | While on, crafts take about 4x as long as with it off (40 ticks instead of 10 for ingots; duration is chosen when a craft starts) and the temperature falls even while working (-0.2 °/tick; -0.6 idle instead of -0.3). See Smelter temperature above. |
| `set_emergency_stop` | `on: boolean` | Smelter | `true`: disables the smelter and marks the stop (`emergency_stop` in the state). `false`: resumes it only if that mark is still set (a no-op otherwise); any `set_enabled` call clears the mark. |
| `set_stock_limit` | `limit: integer`, 1..10 | Assembler | Per-item input cap (default 10); upstream machines are refused at or above it. |
| `set_mode` | `mode: string`, `normal` or `fast` | Assembler | Production mode for crafts starting from now on. `fast` needs `Assembler.FAST_INPUT_MULTIPLIER` (2) times each input and takes the recipe time divided by `Assembler.FAST_TIME_DIVISOR` (2, rounded down, floored at 1 tick); lacking the extra inputs, the assembler waits rather than falling back to `normal`. A craft already running keeps the cost and duration it started with (mode is read only when a new craft starts, same as the Smelter's `cooling`). The sprite is tinted while in fast mode. Values need playtesting. |
| `set_direction` | `direction: integer`, 0..3 (right, down, left, up) | Conveyor | Turns the conveyor. |
| `set_accepting` | `on: boolean` | Collector | Off: refuses every item, sells nothing and blocks the line behind it. |
| `assign_chip` | `machine_id: integer`, `chip_id: integer` | Orchestrator | Calls `Orchestrator.assign_chip(machine_id, chip_id) -> bool`: attaches a registry chip to a machine within range, replacing any chip this Orchestrator previously assigned there. Fails, nothing changes, if the machine is out of range, its assignment is owned by another Orchestrator, the chip id is unknown, or the machine already runs that chip. See "Orchestrator assignment" below. |
| `remove_chip` | `machine_id: integer` | Orchestrator | Calls `Orchestrator.remove_chip(machine_id) -> bool`: detaches the chip this Orchestrator assigned to a machine within range. Fails if this Orchestrator manages no chip there (a player-made assignment, or one owned by another Orchestrator, is never touched). |
| `set_range` | `cells: integer`, 1..8 | Orchestrator | Chebyshev range (a square around the Orchestrator); ownership of an already-assigned machine is unaffected by a range change, but `assign_chip`/`remove_chip` on it are refused while it is out of range. |
| `create_chip` | `name: string`, `description: string`, `prompt: string` | Orchestrator | Calls `Orchestrator.create_chip(...) -> bool`: adds a new chip to the registry, `ChipRessource.created_by` set to this Orchestrator. Fails if the name is empty or already used. Not assigned anywhere yet; follow with `assign_chip`. See "Orchestrator create/revise" below. |
| `revise_chip` | `chip_id: integer`, `description: string`, `prompt: string` | Orchestrator | Calls `Orchestrator.revise_chip(...) -> bool`: rewrites the description/prompt (keeping the name) of a chip this Orchestrator created. Fails for a chip it did not create, one revised too recently, or one without enough recent decisions observed yet. See "Orchestrator create/revise" below. |

`set_enabled(false)` per machine:
| Machine | Effect |
|---------|--------|
| Miner | Stops mining progress, including a running prospect/boost timer (it resumes exactly where it left off once re-enabled; backpressure, unlike disabling, never pauses that timer). An ore already held is still pushed on. |
| Smelter, Assembler | Starts no new craft and pauses a running one (progress is kept, `true` resumes it). A finished output is still pushed on and input is still accepted. The Smelter counts as idle, so it cools -0.3/tick. |
| Conveyor, Collector, Orchestrator | None: `enabled` is stored and reported but their logic never reads it. Use `set_direction` / `set_accepting` / `assign_chip`/`remove_chip` instead. |

State sent with a request (`get_state()`): `type`, `enabled`, `status`, plus Miner `item`, `mine_ticks`, `blocked`, `mode` (`"mining"`, `"prospecting"` or `"boost"`), `mode_ticks_left`; Smelter/Assembler `product`, `needs` (the inputs of the product, scaled by the Assembler's mode), `stock`, `working` (Smelter also `temperature`, `cooling`, `emergency_stop`; Assembler also `stock_limit`, `mode`); Conveyor `direction`, `holding`; Collector `accepting`, `sold`; Orchestrator `range`, `available_chips` (every registry chip: `id`, `name`, `description`, `mine` — true when `created_by` is this Orchestrator), `nearby_machines` (every other non-Orchestrator machine within range: `machine_id`, `type`, `owner` (`"none"`/`"this"`/`"other"`), `chips` (each attached chip's `chip_id`, `name`, `owner`, `outcomes` — `ChipComponent.outcome_counts()`, the last 20 decisions split into `applied`/`none`/`failed`, the evidence `revise_chip` weighs), and `state` — that machine's own `get_state()`, so Miner `mode` and Assembler `mode` are visible to the Orchestrator's chip without it needing any special case). An Orchestrator never lists or manages another Orchestrator, so two Orchestrators in range of each other never see one another (and `get_state()` never recurses into another Orchestrator's own `nearby_machines`).

### Miner prospecting
`start_prospecting` gives a Miner a situational trade-off: give up `PROSPECT_TICKS` (80 ticks, 8s at the default 10Hz) of mining to earn `BOOST_TICKS` (200 ticks, 20s) at `BOOST_RATE` (2x) the pace, against whichever `mine_ticks` is current when the boost starts (so `set_mine_ticks` stays meaningful: it sets the baseline both the normal and the boosted pace scale from). These three constants (`Miner.PROSPECT_TICKS`, `BOOST_TICKS`, `BOOST_RATE`) are the ones to retune from playtesting, not derived from anything else.
- `mode` (`MINING` -> `PROSPECTING` -> `BOOST` -> `MINING`) and `mode_ticks_left` are the whole mechanism: `_tick()` reads the mode a tick started in, counts it down, and only then advances it, so a span lasts exactly its configured number of ticks regardless of when boundaries land. `start_prospecting` and `set_mined_item` are both refused outside `MINING`, so a cycle cannot be restarted mid-way and the mined resource cannot change mid-cycle.
- The mode timer counts down even while the output is blocked (backpressure never pauses it, only `set_enabled(false)` / status `DOWN` do, the same as ordinary mining progress); see `tests/test_miner_prospecting.gd`.
- Starting prospecting preserves the unfinished unit's progress; when the rate changes, its progress is rescaled to the new duration, rounded to whole ticks.
- In-world feedback: a small badge in a corner of the Miner's cell (magnifying glass while prospecting, bolt while boosted), separate from the chip indicator; hidden while mining normally. The tooltip adds an icon + ticks-left row for the same two modes. See `docs/UI.md`.
- Mode and the timer are part of `_save_data()` / `_load_data()`, so they survive save/load like the rest of the Miner's state.

### Orchestrator assignment (prototype, GR2-16)
An Orchestrator (`scripts/machines/orchestrator.gd`) holds no production tools: `assign_chip`/`remove_chip`/`set_range` are its only ones, and they only ever attach/detach a chip through the normal `Machine.attach_chip()`/`detach_chip()` path (the same one the tooltip's "add chip" button uses) — it never edits a chip's prompt and never calls a tool on another machine directly. Once assigned, a chip runs on its own timer/cooldown exactly like a player-attached one; the Orchestrator does not drive its decisions.
- **Ownership, not a separate assignment list:** the only bookkeeping is `ChipComponent.assigned_by` (0 for a player attachment, else the owning Orchestrator's `machine_id`). `assign_chip`/`remove_chip` only ever touch a component this Orchestrator owns; a component with `assigned_by == 0` or another Orchestrator's id is refused, never overridden. This is also how "at most one owner per machine" holds across two Orchestrators with overlapping range: whichever one assigns first owns it until it (or the owning Orchestrator) releases it.
- **Range gates both tools**, every call: `assign_chip`/`remove_chip` are refused on a machine outside the current `range_cells` (Chebyshev distance), even one this Orchestrator already owns. Shrinking range does not revoke ownership, it only blocks managing that machine until the range grows back (or another Orchestrator comes into range — and is then refused too, since ownership is unchanged).
- **Deletion:** `discard()` walks every machine and clears `assigned_by` on any component it owns before freeing itself, so a deleted Orchestrator never leaves a machine permanently locked; the chip stays attached and keeps running, now unowned.
- **Stale data is revalidated at apply time**, not trusted from when the chip's prompt was last sent: `assign_chip` looks up both the target machine and the chip id fresh, so a chip removed from the registry, or a machine that stopped being in range, between the request and the response is refused rather than applied.
- State sent to its own chip (`get_state()`): `range`, `available_chips` (the whole registry), `nearby_machines` (every other machine in range, each with its own `get_state()` under `state`, so Miner `mode` / Assembler `mode` need no special case). See the tool inventory table above.
- Tested in `tests/test_orchestrator.gd`: assign/remove, refusing an out-of-range or already-owned machine, range changes, two Orchestrators with overlapping range, deletion releasing ownership, a chip removed from the registry mid-assignment, and save/load.

### Orchestrator create/revise (prototype, GR2-18)
Besides (re)assigning existing chips (above), an Orchestrator can also author its own: `create_chip` adds a brand new chip to the registry (`ChipRegistry.add(..., created_by)`), and `revise_chip` later rewrites a chip it created, so it can act on what it has observed. Both still only ever touch `ChipRegistry`/`ChipComponent` through the same public methods the UI uses; neither edits a chip in place behind the registry's back.
- **Ownership lives on the chip resource:** `ChipRessource.created_by` (0 for a player-authored chip via `ChipPage`, else the Orchestrator's `machine_id`), the same convention as `ChipComponent.assigned_by` for an assignment. `revise_chip`, and `ChipRegistry.revise()` underneath it, only ever touch a chip with `created_by == machine_id`; a player chip or one made by a different Orchestrator is refused, never overwritten.
- **A player edit claims a generated chip:** saving an edit to any chip through `ChipPage` goes through `ChipRegistry.update()`, which always resets `created_by` to 0, regardless of who made it. From then on no Orchestrator revises that chip again; the player owns it outright, same spirit as a player-made `ChipComponent` assignment never being reassigned automatically.
- **Evidence and cooldown guard revision:** `revise_chip` is refused unless the chip has at least `Orchestrator.MIN_REVISION_EVIDENCE` (5) recent decisions observed across every machine in range currently running it (`ChipComponent.outcome_counts()`, each component's last `ChipComponent.OUTCOME_HISTORY` (20) decisions), and at least `Orchestrator.REVISION_COOLDOWN_TICKS` (300, 30s at 10Hz) have passed since this Orchestrator last revised that chip (`_last_revision_tick`, kept in memory only — a reload may let a revision happen a little sooner than the cooldown would otherwise allow, a minor restart quirk rather than an exploit). Both numbers need playtesting, same as `COST`/`DEFAULT_RANGE`. `revise_chip` keeps the chip's name (every place it is assigned keeps reading the same chip) and only rewrites `description`/`prompt`.
- **Deletion releases created chips too:** `discard()` additionally calls `ChipRegistry.release_created_by(machine_id)`, clearing `created_by` on every chip this Orchestrator made (they keep running wherever assigned; a player can edit them like any other chip from then on), the same spirit as releasing `assigned_by` on the machines it managed.
- **Ownership is scoped to a game:** starting or restoring a game releases prior creator IDs before restoring the saved ones. Saves include generated chips even when unassigned, so their prompts and ownership survive loading without letting a reused machine ID claim a chip from another game.
- **Visible, not textual:** an Orchestrator calls `ChipIndicator.show_management(action)` directly (`"created"`, `"assigned"`, `"revised"` or `"removed"`) on the affected machine's own indicator — its own for a creation, the target machine's for an assignment/removal, every in-range machine currently running the chip for a revision. It borrows the same slot above a machine as a chip's own decision result (spinner, then check/dash/cross) but with distinct lavender badges (`Icons` `managed_created`/`managed_assigned`/`managed_revised`/`managed_removed`) so the two are never confused. `ChipPage` and `ChipRegistryPage` also show a hover badge/tooltip ("Created by Orchestrator #N") on a chip it made.
- Tested in `tests/test_orchestrator.gd` (create/revise gating, ownership, discard release, indicator flashes), `tests/test_chip_registry.gd` (`created_by` on `add`/`update`/`revise`/`import_chip`/`release_created_by`), `tests/test_chip_indicator.gd` (`show_management` icons) and `tests/test_save_game.gd` (`created_by` validated and round-tripped through a save).

### Audio (engine, GR2-28)
- `Sfx` autoload (`scripts/core/sfx.gd`): `Sfx.play(cue: StringName, position := Vector2.INF) -> bool`. Code only names a sound; it never owns players, buses or limits. Returns true when a sound started.
- Cues are data: `SfxCue` (`scripts/core/sfx_cue.gd`: `id`, `stream`, `volume_db`, `pitch_jitter`, `cooldown` s, `max_voices`, `ui`) in the `SfxLibrary` resource `data/sfx.tres` (empty until the sound assets land: add one `SfxCue` sub-resource per sound there). An unknown cue, or one with no stream, is ignored with a single warning per name.
- Buses: `SFX` and `UI` under `Master`, plus a `AudioEffectHardLimiter` on `Master`, are created in code by `Sfx.setup_buses()` at startup (idempotent), so `default_bus_layout.tres` stays untouched. A cue with `ui = true` goes to `UI`, any other to `SFX`; the settings issue reads these buses for the volume sliders.
- Voice limiting: a fixed pool of `Sfx.POOL_SIZE` (16) `AudioStreamPlayer`s, no per-machine nodes. A request is dropped inside its cue's cooldown (real clock). A cue at its `max_voices` replaces its oldest voice. With the pool full, the quietest voice (oldest among equals) is stolen, unless the new sound is quieter than all of them, which is then dropped. So 50 machines asking for the same cue play a couple of voices.
- Position: only attenuates. Screen distance (world distance from the listening camera x zoom) is free up to 500 px, fades linearly in amplitude, and is silent (and not played, so it takes no voice) from 1800 px (`Sfx.distance_attenuation_db()`). `FactoryCamera` registers itself with `Sfx.set_listener()`; with no camera nothing is attenuated. No position (`Vector2.INF`): full volume.
- Pause and scenes: the pool is `PROCESS_MODE_ALWAYS`. While `get_tree().paused`, a `ui` cue plays and a simulation cue is dropped. When the current scene changes (menu, restart, new game) every simulation voice stops; UI voices finish, so a button click is not cut by the scene it opens. `Sfx.stop_all(include_ui := true)` stops everything.
- Headless: runs the same rules on the Dummy audio driver. Tests read the `played(cue, position, volume_db, pitch_scale)` signal, `Sfx.stats` (requested, played, unknown, cooldown, paused, too_far, stolen, dropped) and `Sfx.active_voices()`. Tests in `tests/test_sfx.gd`; they swap `Sfx.library` for their own and put it back, and the last test waits for the audio thread to release stopped streams so no leak is reported.
- Not done here: the sound files, wiring cues to gameplay events, the volume UI.

## Risks and mitigations
1. **Latency or rate limits during the demo:** mock provider, per-chip cooldown, small fast model.
2. **Malformed or unsafe LLM output:** whitelist and clamp in `apply_tool_call`. A failed call leaves the machine on its last settings.
3. **Scene merge conflicts:** each dev owns different scenes, and the base `Machine` scene is frozen after Phase 0.
